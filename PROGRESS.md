## What this is
A general machine-learning library in Rust on Burn: the compute layer applications build on
(operations Burn lacks, in forward, backward and decoding-step forms with kernels for Burn's
backends; layers such as LoRA; autodiff utilities such as activation checkpointing; the modules
training uses, such as losses, optimisers and learning-rate schedules), each part built for a
family of models rather than shaped to one; and inference, a whole trained model in one forward
call, tensors in and tensors out, on Burn and across runtimes, with exits to accelerator
compilers. With Burn beneath it, it is meant to do for Rust what PyTorch does for Python, and
to grow more general, not narrower. Each part is held to values recorded from the
implementation it replaces, and each operation is benchmarked on its own, at the shapes its
workload gives it. The application writes the rest on top of it: modules and training code
shaped to its own model, training loops and training algorithms, the generation loop, a task's
harness.

Built so far: one model family, MobileNetV3-Small with any number of heads (`dash-models`),
trained with `dash-train`'s loss, optimiser and schedule and run by Burn or by other runtimes
behind one `dash-core` trait (tract, IREE, TensorRT, Edge TPU), with a cross-backend
conformance test that holds them to each other and a pure-Rust CPU floor; and operations for
training and decoding that Burn 0.22 does not have: `dash-ops` (attention with grouped key-value heads and the masks models train with, whose backward pass keeps no T x T scores; the gated delta rule, chunked and recurrent; causal depthwise conv1d of any small width, from a given state; the log-probability of chosen tokens and cross-entropy fused with the output layer over a large vocabulary; the low-rank product of LoRA's layers; sampling a decoding step's next token on the device; activation checkpointing — over packed variable-length sequences wherever an operation takes sequences, each with a reference every device runs and CubeCL kernels on every CubeCL runtime whose device offers what they ask) and `dash-lora` (a frozen bf16 base, f32 adapters, several over one base, PEFT's format), which depend on Burn alone.

Where it is going: models defined once in Rust on Burn, trained by the applications that use
them, on dashmag's operations and training modules, and run by dashmag, with ONNX and int8
tflite written from Rust only as exits to NPU vendors' compilers. `dash-train` keeps its
modules; its training loop, data and cache handling, `predict` and command line move to the
application that uses them.

On CUDA with TF32 off, the PyTorch-trained model's 20075 answers on those 4015 frames are PyTorch's too; with TF32 on, one is not (2026-10-25).
- `no_std` floor — not built at all; the MCU claim is unproven.
- `dash-train` trains as well as PyTorch did — missing: a comparison anyone can re-run, on public data. On data this repository does not hold: `dash-train evaluate` and `calibrate` reproduce a PyTorch-trained model's validation report and calibration exactly (2026-10-21); five complete runs on Flex fall no more than 3 standard errors of the difference below five PyTorch runs of the same recipe, per head on two evaluation sets (2026-10-23); the test is one-sided, so it says dash-train is not worse by more than that, not that the two are equal. One of those ten cells passes only because the margin includes dash-train's own spread; it follows which epoch each run's selection kept. Those runs kept only their best epoch, so both trainers ran again keeping every epoch and were compared at fixed epochs (2026-10-25): there that cell shows no gap, so the gap came from selection. The late drift that moved the selection is not selection's: it is there at every fixed epoch, where on validation dash-train's `traffic` head turns cautious about `congested` sooner, by about four of 74 such frames (2.3 standard errors); the two evaluation sets, with 11 and 16 `congested` frames, do not show it. Whether it is dash-train's or chance in those five runs is open: dash-train's side was the same five runs again, so only PyTorch's side was new, and new dash-train runs would tell. A full run on CUDA with TF32 off (2026-10-25) scores inside the range of the five Flex runs, and of those and the five PyTorch runs together, on nine of the ten cells, above both on the tenth; two runs of its seed in separate processes on that GPU keep the same weights bit for bit through the 8 epochs compared.

## Decisions
- 2026-09-04 On NVIDIA silicon TensorRT is the speed tier and IREE the portability tier — because IREE's kernels run at 8-9% of SM compute against TensorRT's 63% on the same GPU, and closing that needs hand-written tuning specs per shape.
- 2026-10-13 Commits carry a GitHub noreply address and merges are fast-forward only — because a forge-made merge commit publishes the merging account's address, which a pull-request check cannot see.
- 2026-10-13 zune-jpeg is built without SIMD — so the host and every board decode through the same scalar code.
- 2026-10-20 Models are defined, trained and run in Rust on Burn; Python, torch.export, iree-turbine and IREE retire; ONNX and int8 tflite become exits written from Rust for TensorRT and the Edge TPU compiler — because one definition that both trains and runs has no format crossing to prove equal, and every board result so far had to be proven across one. The torch.export-on-a-board item is retired with it, not pending.
- 2026-10-20 A Burn model's weights are stored as safetensors in PyTorch's convention (PyTorch's parameter names and layouts) — because such a file is also a PyTorch `state_dict` that any tool reads, and Burn's own record format stopped loading across 0.21 to 0.22.
- 2026-10-20 tract moves from 0.21 to 0.23 — because tract 0.21.11 to 0.21.19 pin `half` to exactly 2.4.1 while Burn 0.22 needs 2.7.1 or later; one lockfile cannot hold both, and cargo's only other answer was to fall back to tract 0.21.10.
- 2026-10-20 TF32 is turned off for comparisons by a patched cubecl-cuda (`patches/cubecl-cuda`, one hunk, opt-in through `CUBECL_CUDA_TF32=0`), not by widening tolerances for it — because every agreement recorded here is per logit at f32 precision, and TF32 rounds each matmul input to 10 mantissa bits. Upstream has the request (https://github.com/tracel-ai/burn/issues/6140); the patch goes when a Burn release has a setting.

- 2026-10-21 Training runs on Flex, the CPU device, until a GPU is free — because a full run takes about 95 minutes on ten cores, and the one other GPU in reach, an RDNA2 card under WSL2, has no ROCm: AMD's WSL support starts at RDNA3.
- 2026-10-24 `dash-models` names no Flex features; `dash-burn` and `dash-train` turn on its SIMD kernels and threads — because the crate that defines the model stays device-agnostic, and which kernels run is decided where the device is chosen.
- 2026-10-25 Training operations Burn lacks live in `dash-ops` and `dash-lora`, which depend on Burn alone — because they extend Burn's backends and share this workspace's Burn pin, its patched cubecl-cuda and its way of holding results to recorded references, while nothing else here depends on them, so they can move out or upstream unchanged.
- 2026-10-25 `fusion` and `autotune` are opt-in features — because they change which kernels every Burn crate in a build runs, and with autotune the kernel depends on timing, so results stop repeating bit for bit between runs; the agreements and the determinism recorded here are made without them.
- 2026-10-26 Dashmag is a general machine-learning library in Rust on Burn, not an inference framework for one model family — because what it holds is general (architectures, training modules, operations, runtimes, exits), and with Burn it is to serve Rust as PyTorch serves Python; the model it was first built for uses it and does not define it.
- 2026-10-26 An operation enters the library for its whole family, not shaped to the model that asked for it: attention for the masks models train with, a causal convolution of any small width — because a library grows by its own logic (one convention across operations, a reference for each, kernels on every CubeCL backend), and a requesting model is one test case among others.
- 2026-10-26 A kernel holds what it asks of the device (units per cube, shared memory, a plane width, the tensor cores' instructions, 64-bit integers, its dtypes) against the device's properties before it launches, and a device that falls short runs the operation's reference — because one CubeCL source compiles for every runtime while devices differ in what they offer, and the reference is what every device has.
- 2026-10-27 Dashmag's scope is the compute layer applications build on, and inference. The compute layer is operations in forward, backward and decoding-step forms with a kernel per backend, layers (LoRA), autodiff utilities (activation checkpointing) and the modules training uses (losses, optimisers, learning-rate schedules), each built for a family of models (transformers for language, convolutional networks), never shaped to one, held to its reference and benchmarked one operation at a time at its workload's shapes. Inference runs trained models, whole models among them (`dash-models` and the runtimes), and whole-model inference is one forward call, tensors in and tensors out. The application writes the rest on top of these: modules, training code and stacks of layers shaped to its one model, its training loop, its training algorithms and their objectives (PPO, GRPO and their kind), the orchestration of a backward pass taken in segments, the generation loop that calls the model step by step, samples, keeps each sequence's state and decides when to stop, the scheduler around that loop, and its task harness. `dash-train` keeps its loss, optimiser and schedule and what is general in its calibration and metrics; its training loop, data and cache handling, `predict` and command line move to the application that uses them — because those are the application's own and change with it, and there are too many training algorithms for a library to hold, while operations generalise; the library's part is that its operations support such uses (states and their gradients, attention against a key-value cache, the gated delta rule's recurrent step, and later sampling on the device) and run fast.
- 2026-10-27 Attention's backward sums the query gradient over the key blocks in a fixed order by default, and with f32 atomics only when asked (`AttentionOptions::deterministic` set to `false`, as flash-attn's `deterministic` the other way round), so that by default its every output repeats bit for bit — because the 2026-10-25 decision makes what does not repeat opt-in, and the atomic sum, FlashAttention-2's five products to the fixed order's seven, buys a quarter of the backward's time (5.16 ms against 6.70 at 6144 causal tokens on an RTX 5070 Ti) at the cost of the query gradient's last bits.
- 2026-10-27 On Apple machines dashmag's operations run on MLX for now, through a `dash-mlx` crate that shares `dash-ops`' contract and tests, while the Burn side keeps Metal and ROCm as targets beside CUDA — because on an Apple M6, Burn's bf16 matmul on Metal reaches 3.5 TFLOPS against MLX's 18.6, and a training step's time is mostly matmul: CubeCL's MSL multiplies on the 8x8 simdgroup matrices, which peak near 5.1 TFLOPS there, while MLX runs its matmuls on the GPU's neural accelerators through Metal 4's tensor operations, which CubeCL does not reach yet (https://github.com/tracel-ai/cubecl/issues/1952). This replaces what the closing of https://github.com/bayanasar/dashmag/issues/12 said, that the MLX counterparts would live in the application and dashmag would not run on Metal.
- 2026-10-28 PEFT's file format lives in `dash-peft`, which depends on no tensor library; `dash-lora` re-exports it, and each backend's LoRA layer implements its `AdapterLayer` — because one implementation of a byte-for-byte format, with the checks applying an adapter makes, serves Burn and MLX alike, and the contract crate stays free of I/O (https://github.com/bayanasar/dashmag/issues/13).

## Open
- Depthwise convolution's backward on Flex is 1.35 s of a 3.0 s training step against 0.13 s for its forward (`cargo run --release -p dash-train --example depthwise_backward`): Flex has a depthwise path for the forward only. The input gradient goes through its transposed convolution, a GEMM per image and channel with an inner dimension of 1; the weight gradient through Burn's generic grouped path, a serial loop over every channel. A depthwise backward kernel in Flex would take most of it; not started.
- Training on CUDA takes 0.88 s a step at batch 128 on an RTX 5070 Ti as this workspace builds Burn, 28.5 minutes a run against about 95 on ten cores with Flex, because the build leaves Burn's autotune off: `burn` comes in with default features off and `cuda` alone, so its kernels fall back to their default strategies, and Nsight Systems puts 44% of the GPU time in direct convolution kernels and 44% in reductions, the slowest of each launched with one or two thread blocks, at most 256 threads on a GPU that holds 107520. With `burn/autotune` added to the features (`--features dash-train/cuda,burn/autotune`), an epoch takes 25 s against 113 s (0.19 s a step), after a first step of 69 s spent tuning, since the tuning cache does not persist; it picks other kernels, so its numbers are not the run's without it, and a run with it no longer repeats bit for bit, since which kernel runs depends on timing; the determinism recorded above holds without it. Without autotune, TF32 makes no difference to the speed: 52.0 s of GPU time over 60 steps with it off, 51.9 s with it on.
- Next on Burn: Flex on an aarch64 board (it passes on an emulated Cortex-A53). Trained PyTorch weights come in through `dash-import` (checkpoint to `model.safetensors`, strict), and `tests/recorded.rs` holds an imported model to logits its old framework recorded. Image preprocessing is already one crate, `dash-image`, for training and inference to share; the workspace is on Rust 1.95 and edition 2024, which Burn 0.22 needs.
- IREE stays until Burn covers its targets, then is archived; tract stays only as an independent check over the exported ONNX.
- `main` is not protected on the forge; the no-direct-push rule is a convention.
- Burn's tensors cannot reach CubeCL's CUDA graphs, and each unfused operation costs 30-40 us of host-side scheduling on WSL2: three threads hand work along in batches of 32 and sleep while idle. A decoding step pays it per kernel (`examples/dispatch_bench.rs`).
- Burn's bf16 matmul stays 14-33% behind cuBLAS with autotune because cubecl-cuda's default LLVM backend drops asynchronous copies and TMA. Its NVRTC backend (`cubecl/cuda-cpp`) reaches the TMA kernels, but one candidate for [6144x3584]x[3584x1024] fails at launch inside autotune and the product is never written, silently; not enabled (`examples/matmul_bench.rs`). Reported upstream (https://github.com/tracel-ai/burn/issues/6234), with fixes proposed for both of its causes (https://github.com/tracel-ai/cubek/pull/961, https://github.com/tracel-ai/cubecl/pull/1935); with them applied to local copies of cubek and cubecl, the C++ backend with autotune comes within 1% and 8% of cuBLAS on the MLP products and 23% behind on the output head, whose 1200 rows make 10 tiles that the traversal's groups of four do not divide. Those figures wait for a release that carries the fixes; until then the backend stays off. Without autotune Burn always runs one strategy, at 6.3 TFLOPS on [6144x3584]x[3584x1024], and offers no setting to pick another: training wants `autotune`.
- The chunked gated delta rule runs on the tensor cores for heads of 32, 64 and 128 in bf16 and f16, 1.01 times fla's device time (1.03 over packed sequences) since its backward moves fewer bytes, against 1.07 and 1.10 for the kernels before in the same rounds (2026-10-28). What is left is not isolated: the first kernel inverts `I + A` in f32 on CUDA cores where fla merges blocks on tensor cores (0.33 ms against 0.20 in fla's three kernels), and the backward's kernel for all but the WY part holds 68.5 KiB of shared memory, one cube per multiprocessor (0.55 ms against fla's 0.40), while fla runs the queries' and keys' l2 normalisation in kernels of their own (0.30 ms) that these fold in; no change has been switched on and off to measure what any of that costs. Heads of 256 still run f32 kernels, three times fla's time. Attention's forward with heads of 256 takes 1.27 times FlashAttention's; it runs 128-query blocks where FlashAttention runs 64, and at that width what this costs has not been measured on an idle card. With heads of 64, blocks of 64 queries take 0.82 to 0.90 times the time of blocks of 128 for every mask, measured by switching (2026-10-28), and bring the forward level with FlashAttention's. Its backward takes 1.25 times FlashAttention's by default and 0.96 with atomics: the difference between the two, measured by switching, comes from summing the query gradient in a fixed order, whose own kernel recomputes the scores and their gradient. FlashAttention-3 orders its atomic additions with semaphores for a deterministic backward near the atomic one's speed; that is not started here.
- `dash-lora`'s `examples/lora_layer.rs` times each pass's runs 100 ms of idle device after the previous pass's, so that a trace sets them apart; on an idle card that is too little work, and within two seconds the card lowers its clocks (memory 13.8 to 7.0 GHz, the multiprocessors to 0.55-2.0 GHz) for the rest of the timed passes, PyTorch's losing more time than these. The figures above are the warm-up's, which runs the passes without gaps; the timed loop is to keep the card busy.
- Upstream, found running on runtimes other than CUDA: cubecl-wgpu registers no plane operations on a CPU device (lavapipe), so `logprob`'s pass takes its reference there although its kernel runs correctly when forced; WGSL spells no infinity, which CubeCL's WGSL compiler emits for `f32::NEG_INFINITY`; Burn 0.22's matmul over an inner dimension of one asks CubeCL's CPU runtime for more shared memory than it has, which the references avoid by multiplying such products out.
- Autotune's choices do not persist: every process tunes each new shape again.
- Sampling trails FlashInfer's fused samplers with the temperature alone and with top-p alone at batch 8 (Not sealed). Both launch one block of 1024 units a row there, so the gap is in a row's work, and where that time goes has not been profiled. The Gumbel pass has cost three logarithms and two divisions a token since it stopped using CubeCL's `log1p`, and a form with two logarithms and one division is known. On flat logits, top-p's cut sends the kernel to its radix passes.
